# 3. 알고리즘 상세

각 절 제목 끝 괄호는 SRS 요구사항 번호다. 숫자는 모두 `config/`의 기본값이고 바꿀 수 있다 (전체 표는 [04](04-decisions.md#4-설정값-전체-표)).

## 3-1. 조향 게이트 (FAT_001~004) — `SteeringGate`

**목적:** 차선 변경·회전·제동처럼 졸음과 상관없이 운전대를 크게 쓰는 순간을 뺀다. 남은 '고속 직진' 구간의 조향만 졸음 판단에 쓴다 (기획서 4-1 원칙 2).

### 통과 조건 (모두 만족)

| 조건 | 제외될 때 `GateReason` | 경계 |
| --- | --- | --- |
| 조향각·차속·기어·방향지시등·브레이크를 모두 앎 | `NO_SIGNAL` | 하나라도 null이면 제외 |
| 시속 60 km 이상 | `LOW_SPEED` | 59.9 제외, 60.0 통과 |
| D단 | `NOT_DRIVE` | P·R·N 제외 |
| 다음 회전 지점 거리를 알면 300 m 이상 | `NEAR_TURN` | 299.9 제외, 300.0 통과 |
| 거리를 모르면(null) 시속 60 km 이상을 5분 연속 유지한 뒤 [제안값] | `TURN_UNKNOWN_HOLD` | 4분 59초 제외, 5분 0초 통과 |
| 방향지시등 켠 구간의 앞 10초·뒤 10초가 아님 | `TURN_SIGNAL` | 100.0~103.0초 켜짐 → 90.0~113.0초 제외, 89.9·113.1초 통과 |
| 브레이크 밟은 구간의 앞 5초·뒤 5초가 아님 | `BRAKE` | 200.0~202.0초 → 195.0~207.0초 제외 |
| 보조 주행이 아님 | `ASSIST` | 다른 이유보다 먼저 표시 (화면 회색) |

### 왜 10초 늦게 확정하나

"방향지시등을 켜기 **10초 전**"도 빼야 한다(FAT_002 비고: 소급 제외). 100초 프레임이 들어온 순간에는 105초에 방향지시등을 켤지 모른다. 그래서 프레임을 최대 10초 줄에 세워 두고, **10초 뒤 프레임이 들어오면** 그때 앞뒤를 모두 보고 확정한다.

```
넣은 프레임:  …  98.0  98.1 … 108.0 (방향지시등 ON 105.0)
확정되는 것:      108.0을 넣는 순간 98.0이 확정 → 105.0이 10초 안에 있으니 TURN_SIGNAL
```

- 앞쪽: 이미 확정한 프레임 가운데 마지막으로 켜졌던 시각과의 차이가 10초 이하면 제외.
- 뒤쪽: 아직 줄에 있는 프레임 가운데 10초 안에 켜진 것이 있으면 제외.
- 운행이 끝나면 `flush()`로 남은 프레임을 "그 뒤 10초 동안 아무것도 안 켜졌다"고 보고 확정한다.

### 목적지가 없을 때 5분 규칙 [제안값]

내비 목적지가 없으면 회전 지점까지의 거리를 모른다. 그래서 "고속도로에 올라탄 뒤"를 대신하는 조건으로, 시속 60 km 이상이 5분 이어진 뒤부터 계산한다.

- 시속 60 km 미만이 **30초를 넘게** 이어지면 5분을 처음부터 다시 센다. 29초 감속 뒤 회복하면 이어서 센다.
- 프레임이 1초 넘게 끊기면(신호 끊김) 그 사이 속도를 모르므로 처음부터 다시 센다 [제안값].
- **데모 영향:** 시나리오 JSON(MSG-11)에는 회전 지점 거리 칸이 없다. 거리를 따로 주지 않으면 모든 시나리오의 첫 5분은 점수가 안 나온다 ([05](05-behavior.md#d2-출발-피로-목적지-없음)).

### 보조 주행만 뺀 판정 (`reasonWithoutAssist`)

판정마다 '보조 주행 조건만 빼고 본 결과'를 따로 들고 있다. 점수는 `reason == PASS`인 프레임만, 안전 우회·인계 품질은 `reasonWithoutAssist == PASS`인 프레임까지 쓴다 (기획서 5-4 "보조 주행 중에도 안전 우회는 그대로").

## 3-2. 방향 전환 찾기 — `SteeringReversalDetector`

**목적:** 조향각 흐름에서 "돌리던 방향이 바뀐 점(극값)"을 찾고, 직전 극값에서 이번 극값까지 얼마나 돌렸는지(크기)를 잰다. 미세·큰 수정은 이 크기로 나눈다.

방법 (조향 반전율 계산에서 쓰는 이력 방식):

1. 첫 샘플을 출발점으로 둔다.
2. 출발점에서 0.5° 이상 움직이면 그쪽을 '지금 방향'으로 정한다.
3. 같은 방향으로 더 가면 '극값 후보'를 계속 옮긴다.
4. 후보에서 **반대로 0.5° 이상 되돌아오면** 후보를 극값으로 확정하고, 직전 극값~이번 극값 크기를 하나 낸다.

```
각도: 0 → 2.0 → 1.4 (되돌아옴 0.6° ≥ 0.5°) → 2.0°짜리 조향 1건 확정 (끝 시각 = 2.0°였던 시각)
각도: 0 → 0.4 → 0.0 → …   0.4°는 0.5° 미만이라 방향 전환으로 보지 않음
```

- 0.5°보다 작은 떨림은 방향 전환이 아니다 [해석]. 그래서 '극값 사이 0.4°' 조향은 아예 생기지 않는다.
- 게이트를 못 넘은 구간을 건너 각도를 이으면 가짜 조향이 생긴다(0°에서 달리다 차선 변경 뒤 8°로 돌아오면 8° 큰 수정처럼 보임). 그래서 **게이트 밖으로 나가거나 프레임이 1초 넘게 끊기면 감지기를 처음부터 다시** 시작한다.
- Float 오차(0.0000001° 수준) 때문에 경계(0.5°, 3.0°, 5.0°, 6.0°)가 어긋나지 않게 0.001° 여유를 둔다 [해석].

## 3-3. 미세 수정·큰 수정 (FAT_006·007)

극값 사이 크기 `a`로 나눈다 (`FatigueConfig.swingClassOf`).

| 크기 | 분류 | 경계 |
| --- | --- | --- |
| 0.5° ≤ a ≤ 3.0° | 미세 수정 | 0.5·3.0 포함 [해석], 3.1 아님 |
| 3.0° < a < 5.0° | 세지 않음 | 3.1~4.9° |
| a ≥ 5.0° | 큰 수정 | 4.9 아님, 5.0 포함 |

시각은 극값 시각(끝)으로 기록하고, 그 시각이 창 안에 있으면 그 창에서 센다.

## 3-4. 멈춤 뒤 급조향 (FAT_008) — `SuddenSteerDetector`

"4초를 **넘게** 변화(최댓값 − 최솟값)가 0.5° **미만**이다가, 1초 **안에** 6° **이상** 꺾음."

1. '멈춤 구간'은 늘 **지금 샘플로 끝나는 가장 긴 구간**(폭 = 최댓값 − 최솟값 < 0.5°)이다. 샘플이 들어오면 구간 끝에 붙이고, 폭이 0.5° 이상이 되면 앞쪽을 필요한 만큼만 잘라 낸다.
2. 새 샘플을 붙였을 때 폭이 0.5° 이상이면 멈춤이 끝났다. 바로 앞 샘플까지의 멈춤 길이(마지막 멈춤 샘플 − 첫 샘플)가 4초를 넘었으면 1초 동안 지켜본다.
3. 마지막 멈춤 샘플 각도에서 6° 이상 벗어난 샘플이 '마지막 멈춤 샘플 + 1.0초' 안에 나오면 1건.

11/10 고침: 전에는 멈춤 구간을 앞에서부터 한 번 자르면 그대로 이어 갔다. 그러면 멈추기 직전 꺾임의 끝 샘플(예: 0.615°) 하나가 구간 맨 앞에 남아, 뒤의 0.148° → 0.005° 멈춤이 0.115° 아래로 내려가는 순간 끊겼다. 4.4초 멈춤이 1.8초 + 2.6초로 나뉘어 급조향을 놓쳤고, 샘플을 읽는 위치가 한 칸만 달라져도 결과가 바뀌었다(drowsy 데모 급조향 5번 중 2~5번만 잡힘).

| 입력 | 결과 |
| --- | --- |
| 멈춤 4.0초 + 1초 안 6° | 0건 (4초를 넘지 않음) |
| 멈춤 4.1초 + 0.9초 안 6° | 1건 |
| 멈춤 4.1초 + 1초 안 5.9° | 0건 |
| 멈춤 4.1초 + 1.1초에 6° | 0건 |
| 멈춤 4.1초 + 한 샘플 만에 6° | 1건 |

'1초'는 마지막 멈춤 샘플부터 재고 1.0초를 포함한다 [해석].

## 3-5. 60초 창·30초 갱신·분당 환산 (FAT_005) — `SteeringMetrics`

- 처음 판정 시각에서 60초 뒤부터 30초마다 지표를 낸다. 300초 연속 통과면 60, 90, …, 300초에 9번.
- 창은 (지금 − 60초, 지금]이다. 미세·큰 수정은 극값 시각, 급조향은 확인 시각으로 창 안을 판단한다.
- **분당 환산:** 창 안 횟수 × 60초 ÷ (창 안에서 게이트를 통과한 시간). 60초 중 45초만 통과해도 같은 운전이면 같은 값이 나온다.
- **유효 조건:** 창 안 통과 시간이 30초 이상이어야 `valid` [제안값]. 모자라면 `GATE_WAIT`로 낸다.
- 통과 시간은 '연이어 통과한 두 판정 사이 간격'(보통 100 ms)을 더한 값이다. 간격이 1초를 넘으면 끊긴 것으로 보고 더하지 않는다.
- 급조향은 **최근 5분 횟수**(분당 환산 안 함)와 **최근 60초 창 안 횟수**(이상 분 판정용) 두 가지를 낸다. 5분은 경계 포함: 295.8초 전 → 셈, 325.8초 전 → 뺌.
- 오늘의 나를 만들기 위해 `reset()` 뒤 누적 합계(통과 시간·미세·큰·급조향 수)도 함께 센다.

## 3-6. f값 (FAT_009~011) — `FatigueFactors`

| f값 | 식 | 기준 20(미세)·4(큰)일 때 예 |
| --- | --- | --- |
| f미세 | clamp((1 − 현재 ÷ 기준) ÷ 0.5, 0, 1) | 20 → 0, 15 → 0.5, 10 → 1, 5 → 1, 25 → 0 |
| f큰 | clamp((현재 ÷ 기준 − 1) ÷ 1.0, 0, 1) | 4 → 0, 6 → 0.5, 8 → 1, 12 → 1, 2 → 0 |
| f급조향 | clamp(최근 5분 급조향 ÷ 2, 0, 1) | 0회 → 0, 1회 → 0.5, 2회 이상 → 1 |

기준이 0일 때 [해석]: f미세는 줄어들 수 없으니 0, f큰은 지금 큰 수정이 하나라도 있으면 1(늘어난 것), 없으면 0.
→ **주의:** 오늘의 나의 큰 수정이 0/분이면, 그 뒤 창에 큰 수정이 하나만 있어도 f큰 = 1이 된다 ([09](09-schedule-todo-limits.md#3-남은-일) 고칠 것 2).

## 3-7. 행동 점수 B·위험 점수 R (FAT_012·019) — `RiskScore`

```
B = 100 × (0.35·f미세 + 0.25·f큰 + 0.40·f급조향)        0~100
R = min(100, B × K)                                     B가 0이면 K와 상관없이 0
```

| 입력 | B | K | R |
| --- | ---: | ---: | ---: |
| (1.0, 0.5, 0.5) | 67.5 | 1.20 | 81.0 |
| 시나리오 1: (0.8, 1.0, 0) | 53.0 | 1.15 | **61.0** (기획서 본문 64는 계산 오류, SRS FAT_012는 61) |
| (0, 0, 0) | 0 | 1.35 | 0 (맥락만으로는 점수를 만들지 않음, FAT_019) |
| B 80 | 80 | 1.35 | 100 (상한) |

- B가 NaN이어도 R은 0으로 막는다. NaN이 지수평균에 들어가면 그 운행 내내 점수가 NaN이 되기 때문이다.
- 조향 원천이 5 Hz 미만이면 미세 수정을 빼고 남은 가중치로 다시 나눈다 (3-15).

## 3-8. 맥락 가중 K (FAT_013~018) — `ContextWeight`

K = 1.00 + 켜진 항목 가중 합, 최대 1.35. 모르는 값(null)은 더하지 않는다.

| 항목 | 가중 | 조건 (경계는 모두 '이상') |
| --- | ---: | --- |
| 오래 운전 | +0.10 | 연속 운전 ≥ 2시간 (119분 → 0, 120분 → +0.10). 앱 타이머 값, 1번 `TripState.continuousDriveSec` |
| 취약 시간대 | +0.10 | 02~07시, 14~17시. 연령대 설정 시 추가: 50대 이상 14~18시, 30~40대 22~02시, 20대 04~08시. 시작 포함·끝 제외 [해석] (01:59 아님, 02:00 맞음, 07:00 아님) |
| 혼자 운전 | +0.05 | 조수석·뒷좌석 착석 0명. 하나라도 모르면 더하지 않음 |
| 실내 더움 | +0.05 | 실내 ≥ 25.0 ℃ (24.9 → 0) |
| 하루 누적 | +0.05 | 최근 24시간 누적 ≥ 4시간 (239분 → 0, 240분 → +0.05) |

- 다섯 개를 모두 더하면 정확히 1.35다. 가중을 키워도 1.35로 자른다.
- 운전 시간은 **초**로 받는다. 1번 TripState가 초를 주므로 엔진 안에서 단위를 바꾸지 않는다 (SIG_010, 10단계).
- 취약 시간대는 4번 예보와 같은 정의를 쓴다 (11/7): 시간대는 `VulnerableTimeRange`(분 단위, 시작 포함·끝 제외), 연령대는 `AgeBand?`(null = 설정 안 함). 값은 `VulnerableTimeDefaults` 한 곳에 있고, 앱이 `FatigueEngine(EngineConfig)`로 만들면 팀 `EngineConfig.vulnerableBaseRanges`·`vulnerableAgeRanges`가 K 계산에 들어간다.
- 취약 시간대 판단은 `ContextWeight.isVulnerableTime(분, 연령대)`로 따로 꺼낼 수 있다. 연결기([3-16](#3-16-엔진-출력-연결기-app--fatiguebridge))가 이 함수로 1번에 '취약 시간대 진입'(INT_001)을 알린다.

## 3-9. 3분 지수평균 (FAT_020) — `RiskSmoother`

```
평활값 ← 평활값 + α × (R − 평활값),   α = 1 − e^(−30초 ÷ 180초) = 0.1535   (처음 값 0)
```

'3분 지수평균'을 **시정수 180초**로 읽었다 [해석]. 계단 입력 0 → 100이면 180초(6번 갱신) 뒤 63.2가 된다 (SRS 합격기준).

| 계속 들어오는 R | 평활값이 60 이상이 되는 때 | 80 이상 |
| --- | --- | --- |
| 61 | 25번째 갱신 = 12분 30초 (FAT_020 비고) | 안 됨 |
| 69 (졸음 B 60 × K 1.15) | 13번째 = 6분 30초 | 안 됨 (69로 수렴) |
| 60 (졸음 B 60 × K 1.00) | **사실상 안 됨** (15분 뒤 59.5) | 안 됨 |
| 92~100 (졸음 + 급조향) | 8번째 = 4분 | 12번째 = 6분 |

- 무효 창(`valid = false`)에서는 갱신하지 않고 마지막 값을 그대로 둔다 (AST_004 "위험 점수 갱신 0회") [해석].
- 휴식 인증 뒤 `resetRiskAfterRest()`는 이 값만 0으로 돌린다 (RES_011).

## 3-10. 무효 창 처리 — `FatigueEngine.evaluate`

30초 갱신 때 아래 순서로 본다.

| 상황 | `valid` | `invalidReason` | f·B·R | 평활값 | 화면 (UI_003) |
| --- | --- | --- | --- | --- | --- |
| 그 갱신 시각의 판정이 보조 주행 | false | `ASSIST` | 0 | 그대로 | 회색 |
| 창 안 통과 시간 30초 미만 | false | `GATE_WAIT` | 0 | 그대로 | '측정 대기' |
| 그 밖 | true | `NONE` | 계산 | 갱신 | 점수 색 |

- 무효여도 지표(분당 횟수·급조향 수)와 K는 그대로 담는다. 화면이 회색으로 보여 줄 수 있게.
- 보조 주행은 '갱신 시각의 판정' 하나로 정한다 [해석]. 창 안에 수동 구간이 남아 있어도 그 순간 크루즈가 켜져 있으면 `ASSIST`다.
- `FatigueState` 기본값은 `valid = false, invalidReason = GATE_WAIT`다. Data Interface 시트는 기본값을 NONE으로 적었지만 valid=false와 맞지 않아 바꿨다 (SRS 수정 요청).

## 3-11. 기준선·출발 피로·민감 모드 (BSL_001·003~007) — `BaselineStore`

### 비교 기준 고르기

| 상황 | 쓰는 기준 (`BaselineSource`) |
| --- | --- |
| 오늘의 나가 있고, 그 15분의 조향 원천이 충분했고, 민감 모드가 아님 | `TODAY` 오늘의 나 |
| 그 밖에 깨어 있던 운행 기록이 3회 이상 | `USUAL` 평소의 나 |
| 그 밖 | `DEFAULT` 기본값 미세 20/분·큰 4/분 [가정] |

- **평소의 나** (BSL_001): `validAwake`인 기록을 `tripId` 순으로 정렬해 최근 10회의 미세·큰 수정 **중앙값**. 3회 미만이면 없음 (BSL_003). 원래 2차지만 BSL_003의 "3회부터 평소의 나"에 필요해 계산은 미리 넣었다. 운행 기록을 저장하는 쪽(BSL_002)은 2차라서 **1차 앱에서는 늘 기본값**이다.
- **오늘의 나** (BSL_004): 이번 운행에서 게이트를 통과한 시간이 누적 **15분이 되는 판정**에서, 그때까지의 누적 횟수 ÷ 15분으로 확정한다. 한 번 정하면 운행이 끝날 때까지 바꾸지 않는다.
- **큰 수정 하한** (11/7, 고칠 것 2) [제안값]: 비교할 때는 기준의 큰 수정을 **2/분 아래로 내리지 않는다**(`BaselineConfig.minReferenceLargePerMin`). 처음 15분에 큰 수정이 없던 운전자는 기준이 0이 되어, 그 뒤 큰 수정 하나에도 f큰 = 1(B +25)이 되고 이상 분의 '1.5배'도 바로 채워졌기 때문이다. 오늘의 나(`state.today`)에는 잰 값을 그대로 두고 비교 기준(`state.reference`)과 출발 피로 비교에만 쓴다. 미세 수정에는 하한을 두지 않는다. 기준을 올리면 원래 미세 수정이 적은 운전자가 늘 '줄었다'(졸음 쪽)로 보이기 때문이다.

### 출발 피로 (BSL_005)

오늘의 나를 확정하는 순간 한 번만, 평소의 나(없으면 기본값)와 비교한다. 아래 셋 중 **2개 이상**이면 출발 피로.

| 조건 | 경계 |
| --- | --- |
| 미세 수정이 기준보다 30% 이상 적음 | −30.0% 만족, −29.9% 아님. 기준 0이면 아님 |
| 큰 수정이 기준의 1.5배 이상 | 1.50배 만족 (기준 0이면 오늘 큰 수정이 있으면 만족) |
| 처음 15분에 급조향 1회 이상 | — |

### 민감 모드 (BSL_006·007)

- 켜지는 때: 출발 피로이거나, 출발 전 컨디션 '졸려요'. `sensitive = departureFatigue || reportedSleepy`.
- 켜지면 비교 기준을 **평소의 나(없으면 기본값)로 고정**한다. 졸린 채 출발한 15분을 '오늘의 정상'으로 삼으면 졸린 조향이 0점이 되기 때문이다 (기획서 5-1).
- 첫 음성 확인 예정 시각 `firstCheckDueMs` = max(민감 모드가 켜진 시각, 출발 시각) + 15분. '졸려요'를 출발 전에 고르면 출발(첫 D단)부터 15분이다 [해석].
- '개운해요'·'보통'을 고르면 '졸려요'로 켠 민감 모드만 끈다. 출발 피로로 켠 것은 유지.
- "출발 전에 15분 쉬었다 가는 건 어때요?" 권유는 컨디션을 받은 쪽(3번 음성·5번 화면)이 말한다.
- 회복 확인 '느림' 뒤 민감 모드(RES_006)는 4번이 따로 내고, 1번이 OR로 합친다.

## 3-12. 딴짓·졸음 패턴 (PAT_001~003) — `PatternClassifier`

### 1분 칸

30초마다 60초 창이 오므로 바로 이웃한 두 창은 절반이 겹친다. 그래서 첫 창 시각부터 1분씩 칸을 나누고 **칸마다 처음 들어온 창 하나만** 쓴다 [해석]. 창이 오지 않은 칸(앱 정지·신호 끊김)은 '측정 못 함'으로 채운다. 최근 10칸만 본다.

칸 상태: `NORMAL`(정상) / `ABNORMAL`(이상 분) / `UNMEASURED`(측정 못 함: 무효 창이거나 창이 없음).

### 이상 분 (PAT_001)

미세 수정이 기준의 **70% 이하**이면서, 큰 수정이 기준의 **1.5배 이상**이거나 그 창에 **급조향**이 있었던 1분.

| 미세 비율 | 큰 비율 | 급조향 | 이상 분? |
| --- | --- | --- | --- |
| 0.70 | 1.50 | 0 | 예 |
| 0.71 | 1.50 | 0 | 아니오 |
| 0.50 | 1.49 | 0 | 아니오 |
| 0.50 | 1.00 | 1 | 예 |

### 패턴 (PAT_002·003)

| 최근 10칸의 이상 분 | 패턴 |
| --- | --- |
| 0 | `NONE` |
| 6 이상 | `TREND` 추세형 (졸음 쪽) |
| 3 이하이고 이상 분마다 바로 다음 칸이 정상 | `SPIKE` 튐형 (딴짓 쪽) |
| 그 밖 (4~5, 또는 3 이하인데 복귀 못 함) | `AMBIGUOUS` 애매 → 음성 확인으로 정함 |

- 방금 끝난 칸이 이상이면 다음 칸을 아직 못 봤으므로 애매다. 그래서 **딴짓 한 번은 1분 동안 애매였다가 튐형**이 된다 [해석].
- 급조향이 든 칸은 아래 '급조향 칸' 규칙으로도 이상 분이 된다.
- 이상 분 다음 칸이 측정 못 함이면 복귀를 확인 못 한 것으로 보고 애매 [해석].
- 측정 못 한 칸은 이상 분으로 세지 않는다 [해석].
- 졸음이 이어지면 이상 분이 6개 쌓이기 전 5분 동안은 '애매'로 보인다 (복귀가 없으므로).

### 급조향 칸 (11/7, 고칠 것 1) [해석]

칸마다 첫 창만 쓰기 때문에, 운전대를 멈춘 구간과 급조향이 서로 다른 칸으로 갈리면 어느 칸도 '미세 70% 이하 + 급조향'을 채우지 못했다. 딴짓(35초 멈춤 → 7°) 시작 시각을 1초씩 60가지로 옮겨 보니 **18가지(30%)에서 이상 분 0개**였다. 그래서 급조향 하나를 기준으로 한 번 더 본다.

1. 졸음 점수용 조향에서 급조향이 확인되면(`RAPID_STEERING`과 같은 순간), 그 급조향 시각까지의 60초 창(`SteeringMetrics.windowEndingAt`, 30초 갱신과 같은 셈법)으로 이상 분 조건을 본다. 멈춘 구간이 이 창에 들어 있다.
2. 그 60초에 게이트 통과가 30초 이상이고 조건을 만족하면, **그 급조향 시각이 든 칸 하나만** 이상 분으로 매긴다. 칸 k의 첫 창(첫 창 시각 + k분)은 (k−1분, k분]을 보므로 급조향 시각 t가 든 칸은 k = ⌈(t − 첫 창 시각) ÷ 1분⌉이다.
3. 같은 칸이 원래 규칙으로도 이상이면 그대로 1개다. 칸들의 첫 창은 서로 겹치지 않아 급조향 하나가 두 칸에 들어가지 않는다.

결과: 60가지 시작 시각 모두 '이상 분 1개 → 1분 뒤 튐형'. 졸음 시나리오(B·B2)의 추세형 시각과 다른 시나리오 출력은 그대로다 ([05](05-behavior.md#c-딴짓-오늘의-나-확정-뒤)). 먼저 시험해 본 "같은 칸의 두 번째 창이 이상이면 올림" 안은 12가지에서 이상 분이 2개로 겹쳐 버렸다.

### 안전 우회 (PAT_005)

- 급조향이 확인될 때마다(보조 주행 중 포함) 시각을 쌓고, 최근 5분(300.0초 포함 [해석]) 안에 3회가 되면 켠다.
- 상태를 30초마다 내보내므로 순간만 켜면 받는 쪽이 놓칠 수 있다. 그래서 3회째부터 **5분 동안 켜 둔다** [제안값]. 그 사이 다시 조건을 만족하면 그때부터 다시 5분.
- 켜지는 순간 `REPEATED_RAPID_STEERING` 사건을 한 번 낸다. 4회째가 이어져도 사건은 한 번.

## 3-13. 안전 감시 조향 — `SafetySteering`

점수용 감지기와 같은 규칙(방향 전환·급조향)을 `reasonWithoutAssist == PASS` 프레임으로 한 벌 더 돌린다. 보조 주행 중 급조향, 크루즈 해제 직전부터 이어진 멈춤 뒤 급조향을 잡기 위해서다.

| 확인된 것 | 넘기는 곳 | 사건 |
| --- | --- | --- |
| 급조향 | PatternClassifier.onSudden (안전 우회) | 새로 켜지면 `REPEATED_RAPID_STEERING` |
| 급조향 | AssistModeDetector.onSafetySudden (인계 감시 안이면) | `HANDOVER_UNSAFE` |
| 큰 수정 | AssistModeDetector.onSafetyLargeSwing | 기준을 넘으면 `HANDOVER_UNSAFE` |

급조향 1회 사건 `RAPID_STEERING`(→ 2단계)은 점수용 감지기에서만 낸다. 보조 주행 중에는 조향을 졸음 판단에서 빼므로 내지 않는다 (AST_004).

## 3-14. 보조 주행·인계 품질·조작 공백 (AST_001·003·004·006·007·008) — `AssistModeDetector`

### 보조 주행 판정 (프레임마다, 지연 없음)

| 입력 | 판정 `reason` | `assistMode` |
| --- | --- | --- |
| 크루즈 작동 `true` | `CRUISE` | true |
| 조향 값 `null` | `UNCERTAIN` (판정할 수 없어 보조 주행으로 간주, AST_003) | true |
| 크루즈 값 `null` | 일반 (AST_008 [제안]) | false |
| 그 밖 | `NONE` | false |

- 크루즈를 켠 프레임부터 보조 주행, 끈 프레임부터 일반 (≤ 110 ms 기준 만족).
- 조향 값이 다시 들어오면 그 프레임에서 일반으로 돌아온다. 조향 신호 복귀는 인계로 보지 않는다 [해석].
- 매끈한 조향으로 보조 주행 추정(`SMOOTH_STEERING`, AST_002)은 2차라 아직 없다.

### 인계 품질 (AST_007)

- 크루즈가 꺼지는 순간(CRUISE → 그 밖) 30초 인계 감시를 시작한다. 감시 범위는 (해제 시각, 해제 + 30.0초] [해석]. 감시 중 크루즈를 다시 켜면 거기서 끝.
- 감시 안에서 아래 가운데 하나면 **인계 이상**:
  - 멈춤 뒤 급조향 1회 (29초 → 이상, 31초 → 아님)
  - 큰 수정이 평소 해제 때의 1.5배 이상 (평소 기록이 없으면 3회 이상). 평소가 0회면 1회만 나와도 늘어난 것 [해석]
- '평소 해제 때 횟수'는 깨어 있던 최근 운행 10회의 `handoverLargeCount` 중앙값 [해석]. 1차에는 기록 저장이 없어 늘 '기록 없음 → 3회' 기준이다.
- 해제 한 번에 사건은 한 번. `handoverAbnormal`은 받는 쪽이 놓치지 않게 30초 동안 true로 둔다 [해석].

### 조작 공백 (AST_006)

마지막 조작 뒤 지난 초를 `opGapSec`으로 낸다. 조작은 방향지시등 켜짐, 브레이크, 크루즈 켜고 끄기, 크루즈 설정 속도 변경, 통풍 단계 변경이다. 공조 온도 조작은 신호가 정해지지 않아 빠져 있다 [해석]. 첫 프레임부터 센다. 900초 → 900, 901초 → 901. "15분을 넘으면 확인을 당김"은 1번이 이 값을 보고 한다.

## 3-15. 조향 원천이 5 Hz 미만일 때 (SIG_009 엔진 쪽)

1번 Hub는 항상 10 Hz로 발행하지만, 조향 센서 원천이 2 Hz면 같은 값이 다섯 번씩 반복된다. 그러면 0.5~3° 미세 수정이 뭉개져 '미세 수정 감소 = 졸음'으로 잘못 읽힌다. 그래서:

1. 1번 RateMeter 결과가 `MEASURED`이고 `belowMinimum == false`일 때만 `DriveFrame.steeringRateOk = true`로 넣는다. 측정 전(`WARMING_UP`)·측정 불가(`UNMEASURABLE`)·정보 없음은 false다 — 1번 요청대로 '모름'을 '충분함'으로 보지 않는다.
2. **게이트를 통과한 프레임** 가운데 느린 프레임이 그 60초 창 안에 하나라도 있으면 그 창은 미세 수정을 끈다(`microEnabled = false`, f미세 0). 주차 중 느린 프레임은 상관없다 (10단계).
3. 그 창의 B는 남은 두 가중치로 다시 나눈다 [제안값]: `B = 100 × (0.25·f큰 + 0.40·f급조향) ÷ 0.65`. 큰 수정만 2배면 38.46, 급조향 1회 더하면 69.23.
4. 이상 분도 미세 조건을 빼고 '큰 수정 1.5배 이상 또는 급조향'만 본다 [해석].
5. 처음 15분 동안 게이트 통과 판정 가운데 **10% 이상이 느렸으면** [제안값] 그날은 미세 수정을 믿지 않는다: 출발 피로에서 미세 조건을 빼고(남은 두 조건 모두 만족해야 함), 그 15분으로 만든 오늘의 나를 기준으로 쓰지 않는다. RateMeter의 첫 10초 '측정 중'(15분 중 약 1%) 때문에 출발 피로 데모가 막히지 않게 비율로 본다.

**지금 실제 SDK에서는:** 1번 기록(11/3)에 따르면 Vehicle SDK 조향은 원천 시각을 주지 않아 RateMeter가 `UNMEASURABLE`이 된다. 이 매핑대로면 실제 SDK 조향에서는 미세 수정이 늘 꺼진다. 1번과 정할 일이다 ([09](09-schedule-todo-limits.md#4-위험과-대응)).

## 3-16. 엔진 출력 연결기 (app) — `FatigueBridge`

엔진은 30초 상태와 사건만 낸다. 1번 단계 전환(`InterventionManager`)이 받는 형식으로 바꿔 넣는 것이 app 쪽 `fatigue/FatigueBridge`(계산)와 `FatigueAssessmentRunner`(실행)다 (11/7). ROS로 치면 엔진 노드의 토픽을 1번 노드의 메시지 형식으로 바꿔 다시 내는 브리지 노드다.

프레임 하나마다:

1. 맥락: `contextInputOf(TripState, SignalFrame, 하루 중 분, 연령대)` → `engine.context`. 하루 중 분은 프레임 시각(epoch ms)을 `Asia/Seoul`로 바꾼 것으로, 4번 예보와 같은 해석이다.
2. 취약 시간대가 바뀌면 `VulnerableTimeChanged`. 엔진 K와 같은 함수(`ContextWeight.isVulnerableTime`)라 정의가 하나다.
3. `toDriveFrame(NaviState)` → `engine.push`.
4. `drainEvents()` → `Safety(SafetyEvent)`. 이름이 같은 `SafetyEventType`, 출처는 조향 값의 출처(모르면 차속의 출처, 그것도 모르면 REAL) [해석].
