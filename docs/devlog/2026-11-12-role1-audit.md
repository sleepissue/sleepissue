## 새로 재현한 문제와 첫 수정

### A. REAL 저장은 실제 제품의 최신 단계/위치를 받지 못함 — 아직 미수정

`PlaygroundTripSession`의 TripTracker와 `MonitoringPipeline.manager`가 따로 생성된다. 전자는 운행을 저장하지만 후자의 현재 단계·Hub 위치를 반영하는 배선이 없다. `RealTripCheckpointCodec`은 gear/power만 보관한다. 같은 조립을 이용한 재현에서 현재 manager는 REST_GUIDANCE인데 저장/복원 단계는 NORMAL, 현재 위치37.5/127.0인데 저장 위치null이었다. baselineRef도 공급 연결이 없다. Room serializer가 값을 잃는 문제와 구분한다.

- [재현 값](evidence/2026-11-11-role1-audit/real-checkpoint.json), [실패 XML](evidence/2026-11-11-role1-audit/jvm-reproduction-failures.xml).
- 수정 시작 뒤 AVAILABLE/REAL 품질을 명시한 위치로 다시 고정 재현해 **1개 실행/1개 실패**를 별도 보존했다. [유효 입력 재현](evidence/2026-11-12-role1-fixes/real-checkpoint-available-input.json) · [재현 소스](evidence/2026-11-12-role1-fixes/RealCheckpointAuditTest.kt). 정상781개 회귀와 별도이며 이 결함은 미수정이다. 임시 fixture는 정상 source set에서 제거했다.
- 기존 boot fixture는 이미 채운10종이 살아남는지 검증했다. 현재 파이프라인이10종을 올바르게 채우는지까지 보장하지 않는다.
- 다음 수정은 실제 snapshot 공급 계약, 개입 checkpoint의 REAL 시계/요청 타이머 복원, 기준선 export/import를 구분해 설계해야 한다. 과거 점수·현재 기어·음성/경유지 요청을 부팅 직후 재실행해서는 안 된다.

### B. 첫 확인 예약/화면 컨디션 전달 누락 — 이번 수정

2번은 `BaselineState.firstCheckDueMs`를 제공했지만 받는 `InterventionInput`이 없었다. 새 재현에서 민감 모드/예정 시각 도달에도 NORMAL·확인 요청 없음이었다. UI의 selectedSleepy도 화면끼리만 전달됐다.

- `FirstCheckScheduled` 입력과 변경 시 전달을 추가했다. 민감 모드 종료/휴식 인증은 예약 해제, 예정 시각 이후 **DRIVING 새 입력**에서 한 번만 확인한다. 점수의0/30/60초 상승은 유지한다. BSL006/007의 명시적 첫 예약 확인은 점수 상승과 분리해 CHECK로 진입하며 안전 우회·3단계는 낮추지 않는다.
- 화면 선택→서비스 Intent→StateFlow→Runner 배선. 최초 D단의 engine reset 뒤 선택을 다시 적용한다. 그 뒤 새 운행에는 과거 졸려요 선택을 자동 복사하지 않는다.
- DEMO owner codec v2에 예정 시각 추가, v1 읽기 유지. REAL의 전체 학습창/개입 복원 해결을 뜻하지 않는다.
- 기획 근거: 현재기능5-1 및 `docs/fatigue-engine/08-team-handoff.md`의5b/인계 요청. [수정 전 값](evidence/2026-11-11-role1-audit/first-check.json).

### C. 자동 추가 뒤 취소 — 아직 미수정

`PolicyInterventionManager.cancel`은 완료된 ADD_WAYPOINT에 FAILED/NOT_SUPPORTED를 반환한다. `RestAreaRestPort`의 REMOVE도 미지원이다. 기존 시험 이름에 “제거 성공을 꾸미지 않음”이 있어 올바르게 미지원 반환을 검증하지만 INT010의 “취소 시 실제 제거”를 충족하지 않는다. 1번 manager/router·4번 공개 NaviBridge 제거 계약·5번 취소 UI를 연결해야 한다. 이번 실제 내비 경유지는 조작하지 않았다.

### D. 출발 피로 제품 데모 — 실제 기기 실패, 미수정

원본 departure JSON·제품 Controller→Player→Hub→기존 엔진 경로에서15분15초까지 출발 피로가 false였다. 처음900초는10배, 그 뒤1배인 원본 설정을 사용했다.9,151개 전달, 실제 약105초 측정. 점수/단계/응답 결과 주입 없음. 기존 default 기준선의 MVP 조건이며 TC의 평소3회/60배 fixture 전체를 수행한 것은 아니다.

대조군은 원본18,000개를 이상적인100ms 간격으로 직접 FatigueBridge에 넣었다. 이때 departure는910,000ms에서 true가 됐다. 엔진의10초 지연/유효 게이트와 제품의 배송·소비 차이를 분리해야 한다. JSON 내용을 임의로 강하게 바꾸거나 시각/TTL을 바꿔 통과시키지 않았다. CPU가 원인인지 특정되지 않았다. [제품 실제값](evidence/2026-11-11-role1-audit/departure-device.json) · [이상적 대조군6종](evidence/2026-11-11-role1-audit/six-scenario-engine-control.json).

### E. 서비스 음성·제품 조립 — 일부 미완

REAL 서비스는 specialUse만 선언됐고 microphone FGS 유형/화면 표시 후 시작 gate/그 이전 대체 경고가 없다. Occupancy에는 microphoneAvailable=true/speechDetected=false가 고정, CabinMonitor 배선이 없다. 녹음 fallback cue map은 emptyMap이다. Rest 화면/버튼 일부는 아직 기본값 기반이다. 제품 데모의 “민감 모드” 표시는 현재 departureFatigue를 표시하므로 보고된 졸려요만으로 켜진 sensitive까지 표현하는 UI 연결도 남는다. 사용자1번의 서비스·통합 대표 범위와3/4/5번 협업 범위를 나눠 진행할 일이다.

실제 TTS1배속→종료10배속은 확인했지만 감사 중 질문 결과는 **FAILED(마이크 권한 미허용)**였다. fixture의 completed=true를 사람의 정상 응답 성공으로 바꾸지 않는다.

### F. Lint 두 오류 — 이번 수정

전체 Lint에서 AudioRecord 권한 검사 누락과 Compose 중 StateFlow.value 읽기 오류를 찾았다. AudioRecord 전에 RECORD_AUDIO를 명시 검사하고 기존 예외 처리도 유지했다. 제품 화면의 sampled flow 초기값은 null로 두고 수집값으로 갱신한다. 경고210건은 별도 기존 정적 검사 항목이며 무시/일괄 억제하지 않았다.

### G. JSON 스키마 경계 — 제품 로더 실패가 아님

공용 schema는 README에 명시된 canonical `schemaVersion/id/startEpochMs/samples.t` 형식이다. 팀 원본6종은 `formatVersion/scenarioId/startAt/tMs`다. raw를 canonical jsonschema에 바로 넣으면6/6 거절되지만 **DemoJsonLoader는 두 형식을 정규화해 받아들이며 제품6종 버튼/원문 APK가 실제 통과**한다. 외부 스키마 검사 절차/변환 도구를 맞출 작업이지 제품 재생 미구현으로 분류하지 않는다.
