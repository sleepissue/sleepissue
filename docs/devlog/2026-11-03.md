## 원인과 수정

`PolicyInterventionManager`는 미완료 운전자 확인을 `checkRequired`에 포함한다. 이 신호는 확인이 끝나기 전에 2단계가 내려가는 것을 막는 데 필요하다. 문제는 순수 정책이 점수·추세형으로 목표 3단계를 골라 놓고도, 사유를 고를 때 `pendingCheck`나 시간·예보를 먼저 보던 것이었다. Manager는 잘못된 사유를 `restCue()`로 받아 안전 안내를 만들었다.

`InterventionPolicy`의 일반 상승 사유 선택에서 목표가 `REST_GUIDANCE`면 `SCORE`를 먼저 선택한다. 이 일반 경로의 3단계 목표는 점수·추세형 조건에서만 결정된다. 확인 대기·시간/예보 입력은 지우지 않고 각각 기존 2단계·1단계 조건으로 사용한다. 앞선 명시적 안전 우회·사람 확인 결과·정상 회복 우선 분기, 30초 간격, 하강·인증·재안내 규칙도 유지했다.

### 저장·복원 구조

`app/data/TripDatabase` v1은 상태 한 행과 순서 있는 `drive_segment`들을 트랜잭션으로 교체한다. 외래 키 cascade와 일관된 읽기를 사용하며 부분 실패는 전체 rollback한다. 파괴적 마이그레이션은 사용하지 않는다. 스키마를 `app/schemas/`에 내보내고 DB를 클라우드 백업·기기 이전에서 제외했다.

`RoomTripRepository`는 기존 포트를 구현한다. 공개 초 카운터 외에 **연속 ms·정차 전 연속 ms·잠정 정차·마지막 관측·OFF 시작·새 운행 대기·휴식 초기화 통지 여부**와 계산 정책·출처·시간축·저장 3시각을 보관한다. 최근 24시간 합계는 구간으로 재계산한다. Android 비의존 `TripSnapshotValidator`와 app의 버전 있는 `TripSessionCodec`가 공개/정밀 상태·구간·관측·단계·인증 근거를 검증한다. 공개 값만 있는 예전 스냅샷을 정상 저장·복원으로 처리하지 않는다.

개입 체크포인트에는 상승/하강 기준 시각·시간/예보 유지·느림 횟수·정상 확인·민감/취약 조건·인증 세션·회복 완료·재확인 가능 시각을 저장한다. 재실행 시 **새 Tracker·Store·Manager를 같은 저장 세대로 구성**한다. 복원 자체는 정책 재평가나 음성/검색/경유지 발행을 하지 않는다. 과거 실행 요청 ID·음성 원문·오디오·후보/자동 추가 예약은 복원하지 않는다. 중단된 확인은 남은 가상 대기 시각을 지킨 뒤 사용자가 명시적으로 새 ID로 요청한다.

Room runtime/compiler **2.8.5**, KSP2 **2.3.13**만 app에 추가했다. [Room 공식 릴리스·호환 조건](https://developer.android.com/jetpack/androidx/releases/room), [AGP 내장 Kotlin의 KSP 안내](https://developer.android.com/build/migrate-to-built-in-kotlin), [KSP 공식 릴리스](https://github.com/google/ksp/releases)를 확인했다. 기존 AGP 9.4.0·Kotlin 2.4.21·Gradle 9.6.0·minSdk 28·compile/target 37은 유지했다. Room/KSP의 개별 공식 조건과 실제 빌드 결과를 근거로 삼으며 전체 조합의 공식 보증으로 확대하지 않는다.

### 시계·실패·삭제 의미

`TripSaveCoordinator`는 기존 `EngineConfig.stateSaveIntervalMs=10_000`을 사용한다. 가상 모드는 수동 관측 10초마다, 실제 모드는 `elapsedRealtime` 10초마다 저장한다. 화면 소유 코루틴이 약 1초 간격으로 확인한다. 즉시 저장은 주기와 무관하며 성공한 뒤 자동 저장을 재개한다. 상태·구간·개입을 함께 캡처하며 실패한 저장은 마지막 성공 시각·횟수를 갱신하지 않는다.

수동 운행 시각은 저장된 가상 시각부터 이어진다. 기기 날짜·실제 경과 시각은 저장 메타데이터로 구별하며 종료 중 실제 시간을 운전/정차에 더하지 않는다. 앱 종료는 OFF 입력을 만들지 않는다. REAL 입력은 수동 세션의 현재 신호로 재사용하지 않고 `STALE_INPUT`, 실제 경과 운행 시간축은 `UNSUPPORTED_TIME_BASIS`로 구별한다. 손상·구간 누락·단계 불일치·소유자 입력 불일치·미지원 버전은 실패이며 빈 DB와 구별한다. 복원 실패 시 DB를 보존하고 자동 저장을 중지한다.

전체 테스트 상태 초기화는 **메모리만 교체하고 DB 보존**, 저장 데이터 삭제는 **메모리 유지·DB 삭제**다. 둘 다 자동 저장을 중지해 의도치 않은 덮어쓰기·즉시 재생성을 막는다. 사용자가 즉시 저장 또는 자동 저장 재개를 선택하면 현재 메모리를 다시 저장한다. 디버그 상단에 저장/복원 상태·실패 사유·마지막 성공 가상/기기 시각·자동 저장 기준과 정차 전 연속/잠정 정차를 표시한다.

버튼별 단계·종료 명령·기대 결과는 [Room 사용 가이드](../setup/ROLE1_PERSISTENCE.md)에 정리했다. 큰 가상 이동은 중간 관측과 DB 쓰기를 모두 실행하므로 목표 시각과 ‘가상 시간 진행 완료’를 확인한 후 다음 버튼을 누른다.

### 보존 확인과 남은 순서

작업 시작 전 파일 사본/해시와 대조해 기존 `InterventionPolicy`·정책 시험·`DebugHarnessControllerTest`·`TripRules`·`RollingDriveWindow`·`TripTracker`·`TripStateStore`·`VehicleSignalHub`를 그대로 보존했다. 다음 구현은 앞선 인계 순서대로 **Hub 발행·품질/중재 → 공식 SDK 어댑터와 targetSdk 정합성 별도 검증 → DemoClock/JSON → 감시 서비스·전원/부팅·외부 담당/최종 UI 통합**이다. 실제 차량 운행 시간축 복원은 SDK의 신선한 관측·실제 OFF 근거·재부팅 전후 시간 변환 계약을 확정한 뒤 서비스/부팅 단계와 함께 검증한다. 디버그 DB를 제품 세션 DB로 그대로 오인해 연결하지 않는다.

### 구현과 정책

`VehicleSignalHub`는 두 생성 경로를 공유 계약으로 제공한다. 기존 입력당 한 번 전달하는 코드는 `ObservationSignalHub`로 옮겨 보존하고, `DebugHarnessController`에서 `observations()`로 명시했다. `SignalNormalizer`와 `UnitConverter`를 공유한다. 기존 수동 시계·개입·Room 경로에 주기 타이머를 붙이지 않는다.

새 `PeriodicSignalHub`는 출처별 Source 소유자와 `HubPolicy`를 받는다. `EngineConfig`의 100ms 프레임·1,000ms 내비 간격, 주입 Clock, 자동/수동 Tick을 사용한다. 원천 수집은 느린 출력 소비자를 기다리지 않는다. 출력/원천 관찰 Flow는 replay 0·추가 대기 1·DROP_OLDEST이며, 출력 프레임의 세션/순번으로 소비자 누락을 확인한다. 늦은 Tick은 과거 프레임을 꾸미지 않고 현재 한 장·놓친 deadline 수를 제공한다. [SharedFlow 공식 버퍼 계약](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-shared-flow/)을 확인했고 기존 Coroutines 버전은 유지했다.

입력 완료·실패·명시적 중단은 해당 채널을 무효화하고 다른 입력은 계속 받는다. Hub가 동작 중이면 양쪽 불가도 null 품질 프레임으로 알린다. stop 반환 뒤 새 발행은 없고 캐시·구독을 비운다. 재시작 시 원천 계수·측정 창·선택 유지 조건과 버퍼 세대를 초기화한다. 이미 전달돼 소비자 콜백에서 처리 중인 작업은 소유자가 별도로 취소한다.

`engine/signal/SignalSelection`은 필드별 관측/수신 경과와 출처를 보존해 최신성을 평가한다. 미확정 TTL·원천 시각 누락 허용·REAL 상실 유지/대체는 기본값 없는 정책으로 주입한다. 완전 관측의 null은 이전 값을 지우고, 부분 갱신은 `updatedFields`를 명시한 경우만 허용한다. 보관 값의 재발행은 원천/수신 시각·원천 번호를 바꾸지 않는다.

유효 REAL 우선과 DEMO 대체는 필드별로 독립적이다. 위치는 동일 출처·관측 시각/시간축·수신 세대의 완전한 위경도 쌍만 선택한다. 유효 DEMO 쌍을 먼저 쓰고 없으면 REAL 쌍을 쓰며 혼합 좌표를 만들지 않는다. 방향·남은 시간/거리·회전 거리는 일반 REAL 우선이다. 최종 품질의 `selectionReason`과 선택되지 않은 입력의 진단 품질도 노출한다.

`RateMeter`는 원천 `(now−10초, now]` 창의 고유 관측 시각을 센다. 시작 직후 WARMING_UP, 알려진 활성 창의 무관측은 측정한 0Hz, 중단은 INTERRUPTED/null, UNKNOWN/WALL·역행·오류는 UNMEASURABLE/null이다. 구독 직전 생성된 자료는 감시 창 밖으로 제외한다. 같은 원천 시각은 중복이고 동일 값의 새 시각은 관측이다. REAL 원천의 ELAPSED_REALTIME과 DEMO 원본의 SCENARIO를 분리한다. 60배 시나리오 이동이 REAL 창·Hz를 앞당기지 않는 시험을 포함한다.

선택 조향의 `quality.sourceRateInfo`에 측정 상태·시간축·hz·belowMinimum·계수를 프레임과 함께 담는다. 2번 담당은 null을 ‘충분한 Hz’로 해석하지 않아야 하며, 지표 비활성·B 재정규화는 직접 연결해야 한다.

### 검증 화면과 자동 시험

기존 개발 화면 상단에서 **Hub 가짜 REAL/DEMO 검증**을 연다. 별도 `DebugHubProbeController`·가짜 시계·입력·캐시를 사용하며 Tracker·Store·Room을 소유하지 않는다. 원천/발행 Hz·계수·최종 값/출처/가용성/경과·선택 이유, REAL/DEMO 시작·중단·값 변경, 관측만 일시정지, 2/5/10Hz, 조향 미지원/권한/오류, DEMO 좌표 유무·중지/재시작을 직접 조작한다. ### 보존과 다음 순서

작업 시작 사본과 해시를 대조해 Room 코드·Codec·스키마, TripTracker/Store/운행 규칙, 개입 정책/Manager·기존 시험, Gradle/의존성/SDK 설정 30개 파일이 동일함을 확인했다. 기존 수동 조립 변경은 Hub의 관측 생성 경로 명시 한 줄이고, 기존 개발 기록 원문은 보존한 채 이 절을 추가했다. engine의 Android/AndroidX import가 없고 release 매니페스트에서 두 개발 Activity가 제외됨을 확인했다.

다음 순서는 **공식 SDK 어댑터·권한/지원/단위/원천 시간축 확인 → DemoClock/JSON → 서비스·전원/부팅·다른 담당/최종 UI 통합**이다. 제품 TTL·REAL 상실 유지시간·관측 시각 없는 입력 허용은 담당 합의가 필요하다. 실제 Playground 원천 Hz·60초 발행 성능·Virtual Console 동시 중재·실제 capability 오류 시험, TRP_003 전체와 부팅/FGS는 미완료다. 2번의 미세 수정 비활성·B 재정규화와 후속 제품 Tracker의 혼합 출처/유효 구간 연결도 이번 완료 범위로 세지 않는다.
