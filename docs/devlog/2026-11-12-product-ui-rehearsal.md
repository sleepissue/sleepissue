# 2026-11-12 제품 화면 전체 리허설 — 진행 기록

사용자 요청에 따라 실제 제품 Activity의 버튼을 눌러 6종을 확인했다. 직접 발화는 보류했고, 마이크 동의를 시험 동안 끈 뒤 원복한다. 추가 커밋·push는 발화 확인 후 한 번에 묶기로 했으므로 이 변경은 로컬 검증 중이다.

## 제품 데모 동승자 연결 수정

`ProductDemoSession` → `DemoExecution.respondPassenger` → `AndroidDemoExecutionFactory`의 기존 확인 요청으로 연결한다. 운전자에게 음성으로 묻는 정책은 유지한다. 동승자 설정이 꺼졌거나 활성 졸음 확인 요청이 없으면 거절하며, 경유지 동의·회복 확인은 동승자 버튼으로 답하지 못한다. 버튼의 응답 채널은 PASSENGER_BUTTON이고 음성 응답 시간을 만들지 않는다. 마이크 버튼 대체와 음성 확인 모두 같은 결과 규칙을 사용한다.

신규 회귀 시험은 요청 없음·설정 해제·중복 응답 거절과 ‘괜찮아요’의 2단계 유지·‘쉬어 가요’의 즉시 3단계를 확인했다. 전체 앱465개·엔진346개(기존 결과 재사용), 실패/오류/skip0 및 제품·기기시험 APK 빌드 통과.

ProductUiRehearsalDeviceTest는 실제 DrivingPreviewActivity가 소유한 세션을 관찰하며 로드·재생·응답은 화면 버튼으로 수행한다. SDK 실행 없는 별도 세션의 자동 시험과 구분한다.

## 추가 확인 진행

- 정상·파워냅을 10배속으로 재검증했다. 알람 상태·‘파워냅 시간이 끝났습니다’ 화면과 정상 회복 확인은 관찰했지만, ‘지금 깨우기’를 누르는 과정에서 재생 종료·화면 전환과 겹쳐 15초 탐색 시간 초과가 발생했다. 해당 회차도 실패이며, 기상 버튼까지 통과했다고 처리하지 않는다. 엔진의 15분 알람·인증 기준이나 정식 JSON은 변경하지 않았다.
- 실제 내비 성공 장면은 기존 시험의 임시 경로 요청과 8초 대기 절차를 적용해 별도로 확인했으나, 이번 실제 제품 화면에서는 반영 확인 실패로 끝났다. 안내 활성 상태가 충분히 준비됐는지와 SDK 반영 실패 원인은 추가 대조가 필요하다. 3단계·휴식 인증·회복 후 0단계는 통과했다. 이전 자동 시험의 성공 기록으로 이번 화면 검증을 통과 처리하지 않는다. 경유지 실패 안내를 성공 장면으로 편집하지 않는다.
- 경유지 제안 취소는 실제 화면에서 별도 검증해 통과했다(108.706초). ‘제안·자동 추가 대기 취소’ 결과, 3단계 유지, 휴식 인증·회복 정상까지 확인했다. 실제로 추가된 경유지 제거를 검증한 것은 아니다.
- 직접 발화·알람 소리 청취는 사용자 진행 지시 전까지 보류한다. 이번 AVD는 음성을 듣는 검증용으로 사용하지 않았다.

## 영상 촬영 전 문구 점검

실제 SDK를 실행하는 제품 데모에도 알림 화면 하단에 ‘실제 내비 실행 아님’이라는 기존 문구가 남아 있다. 실제 실행·결과 안내와 맞는 문구로 정리할 필요가 있다. 정차로 돌아온 뒤 남는 주행 제한 안내와 DEMO 수신 중 ‘신호 연결 대기’ 표시도 촬영 전에 구분해 점검한다. 이 기록은 해당 문구가 수정됐다는 의미가 아니다.

## 재개 전 화면 검증 상태

6종의 정상·단계 알림·동승자 버튼·휴식 인증 화면을 확인했다. 단, 최초 전체 시험과 10배속 파워냅 재시험·경로 안내 조건 시험은 실패가 남아 전체 합격으로 처리하지 않는다. 촬영 전 미해결 항목은 (1) 파워냅 알람 뒤 기상 버튼 조작, (2) 현재 환경에서 실제 내비 경유지 반영 성공이다. 직접 발화·알람 청취는 별도 보류다.

원본 요약은 [최초 6종](evidence/2026-11-12-product-ui-rehearsal/initial-six.json), [10배속 파워냅](evidence/2026-11-12-product-ui-rehearsal/normal10.json), [임시 경로 요청 조건](evidence/2026-11-12-product-ui-rehearsal/guided.json), [취소 통과](evidence/2026-11-12-product-ui-rehearsal/cancel.json)에 보존했다. 화면 PNG 전체는 앱 cache와 로컬 /tmp/awakedrive-ui-rehearsal에 있다. 추가 커밋·push는 하지 않았다.


## 이어서 검증한 결과 — 기상 버튼·내비 경유지

사용자가 두 미해결 항목의 재개를 요청해 Pleos Connect v2.1.0 AVD를 콜드 부팅했다. 호스트 그래픽 렌더러에서 에뮬레이터 종료가 발생해 소프트웨어 렌더링으로 재시작했다. 직접 발화·소리 청취는 계속 보류했으며, 시험은 마이크 동의를 임시로 끄고 실제 제품 Activity의 버튼으로 수행했다. 정식 시나리오 JSON·15분 기준·SDK 성공 판정은 변경하지 않았다.

- **파워냅 기상 버튼 통과:** 정상 10배속, 알람 상태 관찰 → 화면의 ‘지금 깨우기’ 클릭 → `NapState.Idle` 및 ‘기상 완료’ 세션 상태 확인. 27,100개 원본 전달·COMPLETED, 기기시험 `OK (1 test)`, 298.722초. 이전 시험은 알람 캡처 도중 재생 종료와 신호 무효화가 겹쳐 버튼이 비활성화됐다. 기상 조작을 캡처보다 먼저 수행해 검증했다. 이 회차의 최종 `recoveryNormal=false`, 스탬프 0이므로 기상 후 회복 정상·보상까지 새로 통과했다고 해석하지 않는다. [기상 결과](evidence/2026-11-12-product-ui-rehearsal/resume/resume-normal10-priority/normal.json).
- **내비 경유지 통합 시험 통과:** 졸음 60배속, 시험 경로 요청 → 운전자 휴식·경유지 동의 버튼 → SDK `getWaypointInfo`에서 `SA-55-동명-부산`(동명휴게소) 확인 → 내비 화면 표시 → 제품 화면 복귀 → 휴식 인증·스탬프 1개·회복 정상·0단계. 27,100개 원본 전달·COMPLETED, 기기시험 `OK (1 test)`, 138.661초. [결과·SDK 원시 응답](evidence/2026-11-12-product-ui-rehearsal/resume/resume-guided-confirm/drowsy.json), [시험 로그](evidence/2026-11-12-product-ui-rehearsal/resume/resume-guided-confirm/instrumentation.txt), [내비 화면](evidence/2026-11-12-product-ui-rehearsal/resume/resume-guided-confirm/drowsy-navigation.png), [회복 화면](evidence/2026-11-12-product-ui-rehearsal/resume/resume-guided-confirm/drowsy-final.png). SDK가 반환한 경유지 좌표는 0/0이므로 등록 확인은 일치하는 POI ID를 근거로 한다. DEMO 위치와 SDK 내비 위치가 같은 주행이라는 검증은 아니다.

내비 화면 전환 시 `LiveDriveActivity.onStop()`이 데모를 종료해 실행 결과를 버리는 문제를 수정했다. 화면을 떠날 때 재생을 일시정지하고 복귀하면 같은 세션을 이어간다. 종료 시계에 도달했으나 작업 예산 때문에 미전달 원본이 남아 있는 상태에서 재개하면 실패하는 경계도 단위시험으로 재현해 수정했다. 시계를 재시작하지 않고 남은 표본을 모두 전달한 뒤 정상 완료한다. 세션 보존·원본 순서 보존 회귀시험을 추가했다.

앱 단위시험 467개·엔진 346개, 실패/오류/skip 0. 제품·기기시험 APK 빌드 및 최종 제품 재빌드 통과. 중간의 실패·연결 종료 회차는 `evidence/2026-11-12-product-ui-rehearsal/resume/`에 별도로 보존했으며 통과 회차로 바꾸지 않았다. [최종 수치 요약](evidence/2026-11-12-product-ui-rehearsal/resume/summary.json).

이번 재개 범위의 두 미해결 항목은 통과했다. 직접 발화·대화 감지·소리 청취까지 포함한 전체 합격을 뜻하지 않는다. 위 ‘영상 촬영 전 문구 점검’의 부정확한 내비 캡션·주행 제한 잔류 안내는 이번에 수정하지 않았다. 커밋·push는 하지 않았다.


## 직접 음성 검증 착수

사용자가 직접 발화·청취 검증 시작과 준비 완료를 명시해, 소리를 켠 AVD로 재실행하고 PC 마이크 입력을 연결했다. debug `VoiceValidationActivity`에서 안내 재생 완료, 응답 시작 213ms·NORMAL·intent=OK, 말소리 감지 true를 관측했다. 사용자가 안내·신호음 청취와 직접 ‘네’ 발화를 확인했다. 이는 음성 부품 검증이며 제품의 졸음→음성 응답 전체 통합 시험은 아니다. [기기 관측·사용자 확인](evidence/2026-11-12-product-ui-rehearsal/voice/first-device-observation.json).

침묵 검사 첫 회차는 사용자가 발화했다고 알려 제외했다. 재시험은 1,451ms·NORMAL·intent=NONE, 말소리 감지 true였으며, 사용자는 침묵했으나 주변 소음이 있었다고 확인했다. 무소음 침묵 시험 통과로 처리하지 않는다. 임계값은 변경하지 않았다. [주변 소음 조건 관측](evidence/2026-11-12-product-ui-rehearsal/voice/quiet-retry-observation.json).

검사 시작 시점을 맞추기 위해 debug 화면에 수동 대기 모드, 안내음 단독 재생, 침묵 전용 응답 검사, 10초 말소리 단독 검사, 실제 `ToneNapAlarm`의 10초 청취 버튼을 추가했다. 제품의 15분 타이머·알람 규칙은 변경하지 않았다. debug APK 빌드·설치 및 수동 대기 화면 진입 확인. 실제 알람 청취와 조용한 조건 재시험은 아직 남아 있다. 제품의 실내 상황 입력은 현재 `speechDetected=false` 고정이므로 실제 대화 감지 연결도 미완료다. 원본 음성은 저장하지 않았다.


수동 침묵 재검사에서는 `latency=null`·NO_RESPONSE·intent=NONE으로 무응답 판정을 확인했다. 이어지는 CabinMonitor는 true였으므로 대화 감지 정확도는 통과로 처리하지 않는다. 알람 10초 실행 구간은 끝났으나 사용자가 ‘알람 안 들림’으로 확인해 청취 실패로 기록했다. [수동 결과](evidence/2026-11-12-product-ui-rehearsal/voice/manual-alarm-unheard.json).

진단 시 레거시 STREAM_ALARM은 음소거 해제·7/7이었지만, 차량 동적 오디오 라우팅의 ALARM은 bus5_alarm_out·그룹3·gain -25dB(20/45), 들렸던 미디어 신호음은 그룹0·0dB(45/45)였다. 재생 로그에 AudioTrack 프레임 전달이 있어도 청취 성공으로 처리하지 않는다. 출력 그룹 음량을 UI에서 높여 재시험 준비 중이며 앱 알람 코드는 변경하지 않았다. 음량이 원인인지는 재청취 전까지 가설이다.


알람 그룹3 음량을 차량 설정 UI에서 20/45(-25dB) → 35/45(-10dB)로 조정한 뒤, 사용자가 동일한 제품 알람 10초 청취에서 ‘들림’으로 확인했다. 해당 AVD·음량 조건의 알람 청취 통과이며 앱 알람 코드는 변경하지 않았다. 데모 전 알람 전용 그룹 음량도 확인해야 한다. 시험용 AVD는 재검증한 35/45로 유지했다. [사용자 청취 확인](evidence/2026-11-12-product-ui-rehearsal/voice/alarm-heard.json).


알람 청취 확인 후 CabinMonitor 단독 검사를 AVD `hostmicoff` 조건에서 수행했다. `speechDetected=false`, `maxRms=4.9339`, `speechFrames=0`을 확인했고 직후 `hostmicon`으로 복원했다. 앞선 실제 입력 검사에서는 `maxRms=19165.0085`, `speechFrames=167`이 기록됐다. 무입력에서 false가 나오는 부품 동작은 확인됐으나, 입력을 끈 시험은 실제 조용한 실내나 주변 소음 배제 정확도 시험을 대신하지 않는다. [입력 차단 진단](evidence/2026-11-12-product-ui-rehearsal/voice/cabin-hostmic-off.json).


사용자가 조용히 수행한 실제 마이크 검사도 true였고 마지막 수치는 maxRms=27301.9162·speechFrames=158이었다.
