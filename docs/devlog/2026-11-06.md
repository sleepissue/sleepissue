## 수정 이유와 동작

1. `PeriodicSignalHub` 수신은 정규화·캐시·원천 계수 갱신에 집중한다. 전체 진단은 발행·수집 상태 변경 때 만든다. 발행에서 평가한 후보·최신성·Hz를 선택과 진단이 공유한다. 구독자가 없는 raw 관측 복사와 반복 enum Set·품질 copy도 줄였다. **diagnostics는 마지막 발행/상태변경 snapshot**이라는 갱신 시점을 `HubContracts.kt`에 명시했다.
2. `RateMeter`의 boxed Long 큐를 확장 가능한 LongArray 큐로 바꿨다. 창 밖 시각만 제거하며 중복·역행·원천 시간축·warmup 계약을 유지한다.
3. `ScenarioDemoPlayer.pump()`는 완전한 원본 세 채널을 인계한 경계에서 callback을 제공한다. debug Controller는2ms 작업 예산과 따라잡기 중 실제1ms 단위 발행 기회를 사용한다. 밀린 원본이 있으면 다음 묶음 전에 `yield()`로 양보하고 즉시 이어간다. 따라잡았으면 기존1ms 대기를 유지한다. standalone Player의 기본25ms 계약은 유지한다. **단일 emit/소비자 대기는 강제 timeout이 아니므로2ms를 넘길 수 있다.**
4. 화면 전달·요약 문자열·성능/audit snapshot은 주로100ms마다 실행하며, 수동 tick API는 반환할 때 최신 상태를 제공한다. trace는 비트마스크와 원시 상태 비교로 집계하고, 관측 tick과 **서로 다른 null 발행 프레임**을 구분한다. 이전/신규 tick 호출 빈도가 달라 null tick 비율을 직접 개선율로 비교하지 않는다.
5. 세 채널에 독립 원본 수신 audit를 추가했다. 정상 경로는 인덱스·계수·시각 해시 갱신만 한다. 원래 null인 샘플도 원본으로 세며 종료 무효화는 별도다. 현재 debug의 채널별 Hub 구독1개 경로에서 유효하다. Flow 인계 감사와 Hub 차량 callback 수를 함께 대조한다.
6. 종료 전 마지막 Hub 상세와 중지 후 상태를 함께 동결한다. `completedTraces` 통로로 Activity에 전달하여 종료 직후 로드/초기화를 눌러도 앞선 캡처가 사라지지 않게 했다. 최근120초 ring이 비워져도 동결한 종료 자료는 저장할 수 있다. Map 변환·JSON·파일 기록은 Controller 잠금 밖 IO에서 한다. 임시파일 완성 후 교체하여 실패 시 앞선 파일을 보존한다.

TTL1,000ms, JSON 원본 시각, REAL 우선, DEMO 좌표 쌍 예외, 원천 Hz, 실제 단조시계와 배속 시나리오 시간의 구분은 유지했다. 마지막 값 유지·원본 삭제·관측 시각 재기록·과거 발행 프레임 보충은 하지 않았다.

## 미해결 항목과 결과 판정

**예상외null0과600Hz 완전 발행은 미달이다.** 수신·진단 할당과 처리 비용, Hub 발행 횟수·deadline 누락의 개선은 확인했지만, 정상 값 구간의 최신성 실패 개선은 확인하지 못했다. 긴 묶음 뒤에만 발행하던 이전 구현보다 밀린 원본의 STALE 출력이 더 자주 드러난다. 이를 TTL 확대·현재시각 재기록·원본 건너뛰기로 숨기지 않았다.

최종 APK 최초 실행에서는 예상외null5,675tick·실제null발행3,712회도 기록됐다(`final-1-normal.jsonl`). 본 비교의 반복 실행보다 큰 초기 지연이 남는다. 외부 중단 뒤 연속 재측정4회도 실제null79~156회, deadline누락5,123~5,321회가 남았다. cold 실행을 버려서 성공으로 표시하지 않았다.

남은 비용은 원본 세 채널의 rendezvous Flow 인계·스케줄링, 정규화·품질 객체와 발행 후보/프레임 할당, JIT/GC 및 화면/trace 작업이다. 현재 계측으로 각각의 독립 기여를 완전히 분리하지 못했으므로 **[가설]**로 남긴다. 기술적2ms 예산은 단일 emit을 선점하지 못하며, 시스템이 오래 멈추면 보존한 과거 원본을 순서대로 전달하는 동안 실제 관측 나이가 커질 수 있다. 안전한 후속 후보는 원본3채널을 한 번에 인계하는 입력 계약과 snapshot 중복 관측 축소지만, 이번에는 검증하지 않은 새 Hub 입력 API를 추가하지 않았다.

실제 SDK+JSON 동시 수신·TTS/STT·REAL 전환110ms는 이번 기기 시험에 포함되지 않는다. REAL 우선·DEMO 위치 예외·원천 Hz·최신성은 관련 기존/추가 단위시험으로 회귀 검증했다. 정상 전달 때 DEMO 시나리오 원천 Hz는10이며 지연 구간에는 창 기준 수신 관측 수에 따라 낮아진다. 60배라고 원천 Hz를600으로 바꾸지 않았다.

현재 APK를 설치한 같은 AVD는 창을 열어 둔 채 최종 완료 화면을 유지한다. 저장 완료 문구와 종료 자동 파일·수동 고정 파일 모두 확인했다. 실패 시 이전 파일 보존은 자동시험으로 확인했다. 최종 상태·검증값은 [전후 측정 JSON](2026-11-06-demo-performance.json)에 남겼다.

최종 네 실행의 첫 PLAYING 상세→종료 캡처 간격은30,001 / 31,014 / 30,013 / 31,020ms다. 질문 유지 실측은1,027 / 1,034ms였다. 이 간격은 상세 캡처 경계의 값이며 버튼 입구 자체의 독립 시계 교정은 아니다. 최종350시험 후 설치 APK SHA256은 `701ba9d1e335c0329c7a22ed7c888171d34afa4b196f6c10e2442d9e5691dca9`로 빌드 산출물과 기기 base.apk가 일치한다. 모든 기기 재생이 끝난 뒤에도 DB·WAL 논리 전체 데이터를 다시 비교하여 동일함을 확인했다.
