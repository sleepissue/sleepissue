# 2026-11-10 — SIG_016 전체 1초 반영 기기 계측

**결론: 정상 ‘안내 시작’ 터치가 수락된 최종 5회 모두 입력→Hub 전체 1초에 미달했다.** 남은60초/50m와 취소 후null 자체는5/5 확인했다. 첫 제품 SDK 목적지 수신까지1,140~2,001ms, SDK 수신→Hub 반영13~100ms, 입력→Hub1,176~2,101ms, 입력→1Hz 소비자1,675~2,504ms다(아래 bracket·±2ms 참고). 시작/종료는 develop-jdw, HEAD **b0cfc1eb687b5a134c5d778ca86436f11f9c40e5**다. AGENTS.md·최신 현황표·11/9 활성내비/취소 기록과 현재기능 기획서4-2·9장을 읽었다. 기존 untracked `navigation-confirmed.marker`, `perfetto-start.txt` 및 기존 전체파일은 그대로 보존했다. 이미 push된 수집/계측을 다시 만들지 않았다. **이번 추가는 명시 실행 AndroidTest 1개와 문서/텍스트·JSON 근거뿐이며 제품 코드·SDK·Hub 정책·TTL·시계·발행 주기는 바꾸지 않았다.** 커밋/push/PR·브랜치 전환·앱 삭제/초기화/Wipe는 하지 않았다.

## 원문과 측정 시작점

원본은 Downloads의 `AwakeDrive_SRS_TC_v0.2.xlsx`, SHA256 `2ea8c6d0baf3040f146fbbab0d87883f12108354411ffaad1f8e6fb1e95e69da`다. [해당 SRS/TC 행 전체](evidence/2026-11-10-sig016-deadline/requirements.json)를 재추출했다.

- REQ_SIG_016: NaviHelper 목적지 남은 시간·거리를 s·m로 NaviState(MSG-14)에 출력. 수락 기준은 ‘목적지 있음 → ≤1s 안에 remainTimeSec(s)·remainDistM(m) 반영, 목적지 없음 → null’. Must이며 비고에는 ‘1s는 [제안값]’이 있으나 이번에는 그대로 판정했다.
- TC_SIG_016: Emu2.1.0/API34·Console 연결·내비 목적지 설정/해제 가능을 전제로, ‘부산’ 설정→원래 값과 NaviState 비교, 목적지 해제→null 확인. 앱 내부 수신 시점을 시작점으로 정하지 않았다.
- **입력 요청**: 공식 `requestRoute` 호출 직전/직후. Unit 반환은 안내 활성화 성공이 아니다. 첫 호출은1,422ms 소요되므로 시점 하나로 축약하지 않았다.
- **최종 전체 시한의 조작 기준**: 미리보기에서 보이는 ‘안내 시작’ 버튼에 공개 `UiAutomation.injectInputEvent`로 정상 DOWN/UP을 넣은 직전/직후. 정차P/0·내비 패키지·보이는 버튼을 확인했고 좌표는 접근성 노드의 화면 bounds에서 구했다. 수락5/5, 주행제한 우회 없음. 자동 카운트다운 이전의 터치와 이후 경로상태/시작이벤트/값을 함께 남겼다. 입력이 실제 목적지 확정으로 처리된 공급자 내부 순간은 공개되지 않으므로 이 bracket을 내부 commit 시각이라고 부르지 않는다.
- **실제 안내/값 SDK 수신**: 독립 NaviHelper의 `ROUTE_GUIDING`, `onRouteStarted`, `DestinationInfo`를 각각 기록한다. 제품 어댑터의 실제 callback 진입시각은 기존 `SdkReading.receivedMs`로 별도 취득한다. 독립 listener 시각을 제품 수신 시각으로 대체하지 않는다.
- **어댑터**: 실제 `adapter.naviSource.states` collector 진입시각. Main에서 원본 SdkReading과 상태를 같이 기록한다.
- **Hub 반영**: `latestNavi` collector가 새 값을 처음 받은 시각을 상한으로, 해당 `NaviState.tMs`(그 tick의 준비 시작 시각)를 하한으로 둔다. **tMs를 실제 emit 시각으로 부르지 않는다.** 실제 assignment는 이 구간 안이다. 계측용 제품 hook은 추가하지 않았다.
- **소비자**: 실제 `hub.naviSamples` 1Hz 구독의 첫 수신시각. `latestNavi`는100ms tick마다 갱신되며, 1Hz stream과 구별한다. 실제1Hz emit 순간의 단독 probe는 없으므로 소비자시각을 emit시각으로 대체하지 않는다.

모든 기준은 같은 기기의 `SystemClock.elapsedRealtime()` ms다. 호스트/adb 왕복·벽시계로 기기 시간을 추정하거나 재부팅 전후 elapsed를 빼지 않았다. 입력은 `[직전, 직후]`, Hub는 `[tick tMs, collector 수신]`으로 구간을 계산하며, **표의 모든 차이는 두 ms 읽기의 양자화를 보수적으로 ±2ms 추가 허용**한다. 주입 bracket 폭은 최종33~66ms, provider 내부 처리시각은 미공개다. 따라서 전체 지연의 구간을 보고하며 SDK 원천 시각·새 센서 관측 시각을 만든 것이 아니다.

## 원인 분리·수정 판단

1. 요청 반환→실제 안내 모드/routeStarted는 별개다. A의5초대 자동 카운트다운과 첫IPC 대기를 제품 처리시간으로 합쳐 설명하지 않는다.
2. 최종B는 터치→제품 SDK 목적지 수신 자체가1.140~2.001초다. 어댑터 수신 이후만 계측한 결과가 아니며, 새 값 수신 전 구간이 전체 미달의 주요 부분이다. 실제 안내모드 callback을 받은 뒤에도 B2/B3/B5의 Hub 반영 하한은 각각1341/1054/1958ms다. 이미 안내 보고를 받은 시점을 하한의 보조근거로 써도3회는1초를 넘는다. 다만 공급자 내부 목적지 commit 시각을 확정한 것은 아니다.
3. 기존 SDK가 남긴 [최종B PID8328 호출 로그](evidence/2026-11-10-sig016-deadline/navi-sdk-logcat-b.txt)에서 기존1초 `getDestinationInfo` 요청은 확인된다. 예를 들어 B5는 제품 조회가 elapsed9883286ms, 최초 유효목적지callback이9884314ms다. 요청 식별자/원천응답시각이 없어 그 callback을 특정요청과1:1 매칭하거나 공급자 내부의 캐시/큐 지연이라고 단정할 수 없다. 제품poll 대기와 공급자 응답/갱신을 완전히 분리한 근거는 없다. logcat monotonic은 이창elapsed와일치하지만 log는보조자료이며본측정은elapsed직접읽기다.
4. 제품 SDK→어댑터1~11ms, SDK→Hub13~100ms다. 1Hz stream 소비자는SDK 이후503~689ms, 내부Hub갱신보다 추가대기한다. latestNavi가갱신됐다는이유로소비자수신까지동일시각이라고보지않는다.
5. **1번 제품 코드의 명확한 기능결함은 확정하지 못했으므로 제품은 수정하지 않았다.** 공급자응답을기다리지않고 RouteStartInfo/과거cache를목적지값으로채우거나, poll/발행주기를임의로줄이거나, TTL/Clock을바꿔통과시키지않았다. 입력시한은미달·수신전원인은미확정으로유지한다. 추가 고속조회 실험을 시작하지 않았다.
