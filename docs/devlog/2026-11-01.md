## 빌드와 호환성 확인

설정을 바꾸기 전에 `./gradlew :engine:test :app:testDebugUnitTest assembleDebug`를 실행했다. Wrapper 9.6.0 다운로드 후 기본 Java 21에서 데몬 JDK 25를 자동 설치하려고 대기했다. 설치된 Android Studio의 JBR 25.0.3을 발견하여 첫 프로세스를 종료하고, 기존 빌드 설정 그대로 `JAVA_HOME`만 JBR로 지정해 재실행했다. 이때까지 프로젝트의 빌드 설정은 변경하지 않았다.

공식 근거(2026-11-01 확인):

- [AGP 9.4 호환 표](https://developer.android.com/build/releases/agp-9-4-0-release-notes): Gradle 9.6.0, 최대 API 37, Build Tools 36.0.0, 최소 JDK 17. 기존 AGP·Wrapper·compileSdk·targetSdk를 유지한다.
- [Gradle Java 호환 표](https://docs.gradle.org/current/userguide/compatibility.html#java_runtime): Java 25에서 Gradle 실행은 9.1.0 이상 지원. 설치된 Studio JBR 25.0.3을 사용하고 기존 데몬 기준 25는 유지한다. 런타임 JDK와 Java/Kotlin 바이트코드 타깃 11은 별개다.
- [Kotlin Gradle 호환 표](https://kotlinlang.org/docs/gradle-configure-project.html): KGP 2.4.20~2.4.21은 Gradle 7.6.3~9.7.0을 지원한다. JVM/Java 타깃을 명시적으로 일치시킨다.
- [AGP의 KGP 런타임 의존성과 버전 선택](https://developer.android.com/build/releases/agp-9-0-0-release-notes#runtime-dependency-kotlin): AGP가 KGP를 전이 공급하므로 버전 미기재만으로 플러그인 미해결을 단정할 수 없다. 앞선 README의 설명은 실제 빌드 결과를 기준으로 고친다.
- [AGP 내장 Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin): app은 내장 Kotlin을 유지하며 `org.jetbrains.kotlin.android`를 추가하지 않는다. engine은 JVM 플러그인을 사용한다.
- [SDK 패키지 설치](https://developer.android.com/tools/sdkmanager): 설치된 SDK 34는 빌드 수준을 낮추는 근거가 아니다. 기존 라이선스로 AGP가 필요한 Build Tools 36과 Platform 37을 설치하도록 했다.

KGP 호환 표에서 AGP의 완전 지원 상한은 9.3.1이다. JVM 플러그인의 Gradle 지원 근거와 AGP의 내장 Kotlin을 구분하며, 이 프로젝트의 AGP 9.4 조합은 실제 로컬 빌드·시험 결과로 별도 기록한다.

## 구현·검증 결과

### 최초 실패와 수정

- 기존 설정 실행은 `:engine:compileKotlin`에서 실패했다. 실제 메시지: `Inconsistent JVM-target compatibility detected for tasks 'compileJava' (11) and 'compileKotlin' (24)`.
- Kotlin의 JDK 25 타깃 미지원 경고 후 기본 Kotlin 타깃이 24로 잡힌 결과였다. engine의 `compilerOptions.jvmTarget`을 11로 명시했다.
- KGP는 루트 플러그인과 버전 카탈로그에서 2.4.21로 고정했다. app은 내장 Kotlin, engine은 JVM 플러그인이다. Gradle·AGP·데몬 JDK·Java 타깃·compileSdk·targetSdk는 기존 값을 유지했다.
- Flow와 결정적인 코루틴 시험을 위해 app에 Coroutines core/test 1.10.2를 추가했다. Compose·Room·서비스 의존성은 추가하지 않았다.
- 설치된 Android Studio의 JBR 25.0.3으로 실행했다. 로컬 SDK에는 Build Tools 36.0.0, Platform 37.0 revision 2가 추가됐다. 개인 절대 경로·`local.properties`는 커밋 대상에 추가하지 않았다.

## 개인 개발 브랜치에 저장

- 사용자 지시에 따라 개인 개발 브랜치를 `develop-jdw`로 정했다. 전환 전 로컬·원격 추적 목록에 같은 이름의 브랜치는 없었다. 원격 서버의 동명 브랜치 조회는 HTTPS 인증 부재로 확인하지 못했으므로 부재로 단정하지 않는다.
- `feat/signal-scaffold`의 HEAD `04b7589148ae268cf6cf6e68c03a1badf9d457ac`에서 `git switch -c develop-jdw`로 생성·전환했다. 미커밋 변경을 모두 보존했으며 `main`·기존 기능 브랜치의 커밋은 변경하지 않았다.
- A 코드·시험·빌드 설정·관련 문서 32개를 선택적으로 커밋한다. 비밀 파일·local.properties·빌드 생성물·APK·SDK 바이너리는 포함하지 않는다. 앞선 단위 시험 37개(기존 템플릿 1개 포함)와 빌드 성공 이후 기능 코드는 변경하지 않았다.
- 기존 Git 작성자 설정이 없어, 연결된 GitHub 프로필에서 확인한 `JDW1224`와 계정 ID 기반 noreply 주소를 이 저장소의 로컬 작성자로 사용한다.
- 원격 저장 대상과 명령은 `git push --set-upstream origin develop-jdw`다. 원격 반영은 실제 push와 원격 SHA 일치 확인으로 판단하며, 인증 실패를 성공으로 기록하지 않는다. 이 기록 작성 시점에는 로컬 HTTPS 인증이 없고 GitHub 연결의 대상 저장소 조회도 404여서 인증 연결이 필요하다.
- 이번 범위에는 공용 `develop` 생성·PR·merge가 없다. 공용 원격 `develop` 존재 여부도 미확인 상태로 구분한다.
